# 方案撰写 Agent —— 设计说明

> 本文从「设计」视角说明本系统的运行流程、核心决策，以及 Agent（大模型）与程序（确定性代码）之间的分工边界。适合对外讲解，或帮助新成员快速建立整体认知。

---

## 1. 设计定位

本系统要解决的本质问题是：**「写一份完整方案」这件事太大、太模糊，一个人或一个模型一口气做不好。**

于是核心设计思想只有一句话：

> **让机器做它擅长的（拆解、起草、执行），让人做只有人能做的（定方向、给事实、把关质量）。**

整条流程的所有设计，都是从这句话推出来的。

---

## 2. 设计的三条主线原则

### 2.1 方向由人定，内容由机器造

系统要求用户给三样东西，各回答一个问题：

| 输入 | 回答的问题 | 设计意图 |
|---|---|---|
| **目标（Goal）** | 写什么方案 | 一句话定性，划定范围 |
| **模板（Markdown）** | 按什么结构写 | 人给机器「章法」，机器不许乱发挥 |
| **资料（背景文件）** | 依据什么写 | 人给机器「事实」，机器不许编造 |

这是「人机边界」的第一次划分：人只负责表达意图和提供事实，具体怎么写全交给机器。

### 2.2 规划与执行分离

把大脑拆成两个角色：

- **规划 Agent**：只负责「拆」——把模板拆成章节清单，定先后与依赖。
- **执行 Agent**：只负责「写」——一次只写一章，写完就交差。

分开的原因：「拆解」需要全局视野，「写作」需要专注单点。让同一个 Agent 又当导演又当演员，会顾此失彼。这也是业界「Plan-and-Execute（先规划后执行）」范式的通用智慧。

### 2.3 逐章停审，人始终在回路里

每写完一章，系统**主动停下来等人审核**，而不是一口气全写完：

- 通过 → 进入下一章
- 要求修改 → 带意见重写（可来回多轮）

设计意图：方案是「要拿去给人看的严肃文档」，机器写的东西不能直接交付。逐章停审，等于把**质量控制内建到流程里**，而不是等最后一次性返工——那样错会越滚越大。

---

## 3. 用户旅程（设计视角）

```
① 定方向   人给目标 + 模板 + 资料（划清人机边界）
② 触发     系统强制校验「至少有可读资料」，否则不让开工
③ 拆解     规划 Agent 拆出章节清单 + 顺序 + 依赖
④ 起草     执行 Agent 一次写一章，写完就停
⑤ 把关     人审：通过→下一章；打回→带意见重写
⑥ 交付     全部章节审完，拼成完整方案
```

每一步的设计意图：

- **② 为什么强制要资料？** 没有事实依据就开写，机器只能编。系统在源头把「编造」堵死——这是**防错前置**。
- **③ 为什么不是模板的简单镜像？** 规划 Agent 会判断哪些标题值得独立成章、哪些合并、谁依赖谁。**章法由人给，具体怎么拆由机器现场判断**，是灵活性与可控性的平衡。
- **④ 为什么一次只写一章？** 把「大方案」切成「可逐个验收的小单元」，降低单次出错代价——一章写砸只重写一章。
- **⑤ 为什么必须停？** 因为人要在回路里。这决定了它是「协作工具」而非「一键生成器」。

---

## 4. 关键设计决策

### 为什么「进度存数据库」而不是内存？
方案撰写可能跑几十分钟，服务随时可能中断。所有进度（状态、正文、版本、意见、写到一半的断点）都持久化，进程重启能原样接上。这是「持久化优先、可恢复」的设计。

### 为什么「每走一步都重新决策」而不是「排好计划照着执行」？
状态会变：人会把章节打回、服务会中断、依赖会调整。系统不是预先排死一张表，而是**每走一步看一眼当前状态、现场决定下一步**。这叫「状态驱动」，不是「脚本驱动」。

### 为什么「每章一个版本、版本递增」？
为了可追溯：这一章改了几次、每次长什么样都有存档，打回重写时旧版不丢。

### 为什么「实时推送」？
执行是异步且耗时的，前端不靠反复刷新，而是**状态一变就自动更新**，看到的是「活的进度」而不是「等待的黑盒」。

### 为什么「断点续写」？
「写一章」本身也耗时（模型要吐几千字）。写到一半断了就整章重来，既慢又浪费。所以**写到哪存到哪**，断了从断点接着写。这是「渐进式落盘」的设计。

## 5. 边界设计：Agent 做什么，程序做什么

这是整套设计最关键的一条分界线。一句话概括：

> **Agent 只负责「出主意」，程序只负责「执行和把关」——模型负责「聪明」，程序负责「可靠」。**

### 5.1 边界总览

| 维度 | Agent（大模型） | 程序（确定性代码） |
|---|---|---|
| 角色 | 参谋、起草人 | 执行者、裁判 |
| 做的事 | 判断、生成内容 | 校验、执行、持久化、编排 |
| 能碰数据库吗 | **不能** | 能 |
| 可靠吗 | 概率性、会犯错 | 确定性、可控 |

### 5.2 Agent 做什么

**规划 Agent —— 只做「判断」**：看模板 + 资料，决定拆哪些章节、依赖、优先级、这次先写谁，输出结构化决策（`CREATE_PLAN` / `SELECT_TASK` / `REPLAN` / `WAIT`）。

**执行 Agent —— 只做「写」**：读资料，写一章正文 + 摘要，有反馈时按意见改写，输出结构化结果（正文 `content` + 摘要 `summary`）。

**关键约束：Agent 手里只有两个「只读」工具**——`list_sources`（列出资料）、`read_source`（读资料）。它只能「读」资料，读不到状态、改不了任何东西；它连「任务进行到哪了」都只能靠程序喂给它的快照。

### 5.3 程序做什么

程序包办 Agent 之外的一切，其中**最重要的是「校验」这道闸门**：

1. **编排** —— 何时叫 Agent、循环多少次、出错怎么办。
2. **状态管理** —— 所有状态机流转（任务 2 态、章节 5 态）。
3. **校验（核心闸门）** —— Agent 返回的决策先验一遍再决定是否采纳：
   - 拆的章节必须引用真实存在的模板节点（不许凭空造章节）；
   - 依赖不能成环；
   - 选的章节必须处于可执行状态；
   - 有章节等待修改时必须优先改它；
   - 决策类型与当前状态匹配（已有任务就不能再创建计划）。
   - 校验不通过 → 拒绝，非法决策不会落库执行。
4. **持久化** —— 所有写库（状态、正文、版本、反馈、断点）。
5. **并发与恢复** —— 租约防重、崩溃回滚、断点续写。
6. **确定性解析** —— 模板标题树、资料文本提取、依赖与上下文组装。
7. **推送与前端** —— SSE 实时通知、审核交互、超时自动同意。

---

## 6. 边界的四条原则

1. **Agent 是「参谋」，程序是「执行者」**：Agent 只提建议，是否采纳、怎么落地全由程序决定。
2. **Agent 只读，程序才写**：所有「写」动作只能经过程序，Agent 没有写工具，想改也改不了。
3. **程序不判「内容好坏」，只判「结构合不合法」**：程序不评价字句通不通顺（那是人和模型的事），只查规则（引用是否合法、依赖是否成环、选章能否执行）。即「内容层面放手，规则层面兜底」。
4. **Agent 的每次输出都要过「程序闸门」**：模型可以犯错，但程序的校验闸门把错误挡在系统之外，保证状态永远一致、可追溯、可恢复。

---

## 7. 设计取舍

这套系统始终在回答同一个问题：**哪些事交给机器、哪些事必须留给人。**

- 机器做：拆解结构、起草正文、执行重复劳动。
- 人做：定方向、提供事实、做裁决（通过还是打回）。

为了「可靠性」，它主动放弃了「全自动的爽快感」——逐章停审、持久化、断点续写，都是为了让它成为一个**可评审、可追溯、可恢复**的严肃工具，而不是出稿快但不可控的黑盒。

---

## 8. 一句话总结

> 这是一个把「写方案」这件大事，设计成「**人定方向、机器起草、逐章验收**」的协作流水线：机器负责拆解和执行，人负责给事实、把质量关；模型负责「聪明」，程序负责「可靠」，整个过程状态可追溯、中断可恢复，每一章都过过人眼才交付。
